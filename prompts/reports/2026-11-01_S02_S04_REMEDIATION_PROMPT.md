### Verified Findings in Slices S02 and S04

1. **S02-01 (Priority: High) – `crates/humoco-node/src/storage/db.rs:2119`**
   - **Problem & Trace:** `RedbStorage::create_backup` unconditionally removes an existing destination before opening it, without checking whether it resolves to the live source database (`db.rs:2118-2124`). The operator control path forwards arbitrary nonempty non-traversing destinations (`crates/humoco-node/src/control/server.rs:494-500`), and CLI online/offline backup reaches the same operation (`crates/humoco-node/src/cli.rs:2049`, `:2081`). Setting the backup destination to the source path unlinks the live database, creates a replacement containing the current snapshot, and leaves the running engine writing to the original now-unlinked file.
   - **Impact:** Subsequent successful writes, including original signing choices and bans, disappear after restart. The backup operation reports success. A compiled temporary probe using the existing production rlib confirmed: quota 100 before self-backup; backup returns `Ok(0)`; live quota is then changed to 200; reopening the named database returns quota 100. This defeats persistence and can restore older signing history without an immediate local integrity mismatch.
2. **S02-02 (Priority: Medium) – `crates/humoco-node/src/storage/db.rs:843`**
   - **Problem & Trace:** A pruning transaction processes at most 256 expired HMC spend rows (`db.rs:778-782`) but independently removes expired root anchors afterward (`db.rs:843`, `:1664-1685`). The flush prune path instead removes roots first (`db.rs:1699`) and also has a separate 256-spend budget, producing the same committed orphan condition. One expired voucher with 257 spend rows therefore retains a spend while its required root anchor is gone.
   - **Impact:** After an ordinary successful cleanup transaction, committed sync reads fail at the missing-root lookup before they can evaluate expiry (`db.rs:1986-1995`, bounded equivalent `:2082` onward). Shard digests also fail before checking whether the orphan belongs to the requested shard (`crates/humoco-node/src/storage/db/install.rs:713-723`), and paginated source snapshots similarly require the missing root (`crates/humoco-node/src/storage/db/snapshot.rs:240-250`). An expired voucher can temporarily block recovery/sync for unrelated live shards until further cleanup removes every remaining orphan. The temporary production-library probe reproduced exactly 256 pruned spends, one remaining spend, no root, and both `sync HMC lock missing root anchor` and `committed spend lacks root` errors.

3. **S04-01 (Priority: High) – `crates/humoco-node/src/network/transport.rs:2746`**
   - **Problem & Trace:** `connect_peer` authorizes an address using `can_authorize_direct_rpc(&addr, None)` at lines 2708–2716, then accepts the TLS peer after checking only whether its extracted key is banned at lines 2746–2756. It never checks that the actual TLS `NodePubKey` is the identity expected for this endpoint or even an authorized known identity before registering the key, publishing the connection, and returning it at lines 2757–2768. The cached-connection return at lines 2719–2720 has the same missing identity validation. `network/tls.rs:113–122` deliberately accepts self-signed server certificates; `manager.rs:1102–1145` records an unknown authenticated key as `Untrusted` but still publishes its connection.
   - **Impact:** A stale or reassigned endpoint for a learned node can accept a connection under an entirely unknown key and receive requests intended for the learned node, violating the identity-based Shard-Direct authorization boundary. This finding does not claim the ability to forge quorum signatures.
4. **S04-02 (Priority: High) – `crates/humoco-node/src/network/transport.rs:3780`**
   - **Problem & Trace:** The unidirectional heartbeat path first attempts `HeartbeatWirePayload::from_bytes`, then also decodes the unsigned legacy `([u8;32], SocketAddr)` tuple at lines 3644–3645. On tuple success, lines 3780–3794 check only bans and consistency between `hops` and the TLS sender; for a different claimed identity and `hops=1`, they insert the claimed key and arbitrary address through `learn_node_from_gossip`, bypassing the modern origin signature, freshness, deduplication, and ticket validation at lines 3670–3740. The learning wrappers at `manager.rs:1459–1513` ultimately permit insertion of a previously unseen key at `manager.rs:1625–1657` (subject only to the work-score floor).
   - **Impact:** In a low-work/bootstrap network accepting work score 1, an authenticated F2F relay can introduce arbitrary third-party identities and addresses without their first-party signature. These entries immediately become known for direct RPC authorization and start ticket incubation. The existing address-overwrite guard protects an already known identity; this finding concerns creation of an unseen identity.
5. **S04-03 (Priority: Medium) – `crates/humoco-node/src/network/transport.rs:3478`**
   - **Problem & Trace:** Connection admission accepts both F2F friends and learned Shard-Direct peers at lines 3375–3377. Only the unidirectional stream path enforces `can_accept_gossip` for `EquivocationProof` at lines 3608–3620; the bidirectional path has no equivalent gossip barrier, and its restricted-RPC list at lines 3478–3483 omits this message. It invokes `NodeRequestHandler::handle_authenticated` at line 3528, which accepts the proof at lines 526–536 and persists evidence/bans and forwards it at lines 403–431.
   - **Impact:** A learned non-F2F shard peer can inject the fraud-proof gossip stream and trigger durable ban processing and F2F forwarding by selecting a bidirectional stream, despite the explicit F2F-only gossip boundary. Genuine self-proof is still required; forged evidence is not shown to slash an innocent node.
6. **S04-04 (Priority: High) – `crates/humoco-node/src/network/transport.rs:394`**
   - **Problem & Trace:** `NodeRequestHandler::handle_incoming_equivocation_proof` uses `verify_equivocation_first_party` at line 394 even though the handler has an explicit `self.network_id`. That wrapper passes `None` at lines 127–131; its verifier explicitly accepts either network at lines 134–138 and 232–245. Consequently a pair of genuine Testnet-only conflicting approvals is accepted by a Mainnet handler and leads to `commit_slashing_evidence_and_ban` at lines 403–410, although the pair fails verification in Mainnet's domain. Both wire stream directions share this handler.
   - **Impact:** Fraud evidence from a foreign network universe can permanently ban the same node key in the local universe, crossing the required network domain boundary. Mixed-network pairs are correctly rejected; the missing case is a same-foreign-network pair submitted to the other local network.
7. **S04-05 (Priority: Medium) – `crates/humoco-node/src/network/transport.rs:2165`**
   - **Problem & Trace:** `ShardBucketRangeRequest` accepts the full untrusted `u16 bucket_count` at lines 2144–2151, reads all committed shard records at lines 2158–2163, then constructs and serializes every requested bucket at lines 2164–2188 before checking the actual wire ceiling. `bucket_count=u16::MAX` from `start_bucket=0` produces 65,535 fixed-size bucket records: bincode body size is 2,949,085 bytes (2-byte shard + 8-byte vector length + 65,535 × 45 bytes). `checked_payload_len` only checks conversion to `u32`; `framing.rs:921–928` later refuses this body above 65,536 bytes during `write_frame`, called at `transport.rs:3530`. Each requested bucket also scans the entire shard twice (`crypto.rs:434–446` and `transport.rs:2170–2177`) on the async runtime after the storage worker returns.
   - **Impact:** A 12-byte authenticated request causes several MiB of avoidable allocation and up to 65,535 repeated shard scans, and then fails to return a protocol response because the generated result is unsendable. The synchronous loop cannot be preempted by the surrounding Tokio handler timeout while it is running.
