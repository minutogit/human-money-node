## S05-16 — Medium — Token-file permission errors are discarded

Primary reference: `crates/humoco-node/src/api/auth.rs:49–50`.
Related occurrence: `auth.rs:88–89`.

Expected: The token manager's strict POSIX 0600 contract (`auth.rs:28–32`), also
reflected in its existing permission-correction regression, requires file
protection to succeed before returning an active manager. A failure to establish
the required protection must propagate through the existing `io::Result` API.

Observed: For an existing token, `load_or_create` discards the result of
`set_permissions`, then reads the file at line 53 and returns a usable manager.
If a readable 0644 file cannot be changed to 0600, initialization still succeeds
and the token authenticates while remaining readable to other local users.
The post-creation enforcement also discards its error; it is included in the
same error-propagation defect, not counted separately. The demonstrated failure
is on the existing-file path. No remote authentication bypass is claimed.

### Executed reproduction

The agent linked an isolated Rust probe against the current production library.
A Python launcher created an owned temporary regular token file with mode 0644
and applied a child-only seccomp filter returning EPERM for chmod-family syscalls.
The probe confirmed that the real permission operation fails, called the real
`AdminTokenManager::load_or_create`, checked the remaining file mode and used
`verify_token`. No system file or foreign-owned object was modified. The
coordinator inspected both probe sources and independently repeated the launcher.
Both executions exited successfully with:

```text
chmod_error=PermissionDenied; manager_returned_ok=true; remaining_mode=644; token_authenticates=true
```
