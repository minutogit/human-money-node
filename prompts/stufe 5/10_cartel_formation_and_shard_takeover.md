# Audit 10 — Cartel formation and shard takeover

Date: 2026-10-25. Snapshot: `9a28517d0a02e34721c102bccbf786b8443c3664`; isolated tests only. No production fixes.

## Findings

**A10-01 · P2 · A verified permanent ban can disappear on engine reload when persistence is unavailable.** `crates/humoco-node/src/storage/engine.rs:1090–1112` publishes the ban in RAM but drops `FlushOp::BanNode` when its channel is full/closed. The proof receiver stores evidence separately (`network/transport.rs:433–443`); startup imports the ban table, not a replay of stored evidence (`daemon.rs:472–487`). A real-QUIC probe aborted the persistence worker, delivered a genuinely signed same-slot equivocation proof and received an acknowledgment. Observed: `ram_ban=true`, `disk_ban=false`, `evidence=true`, and a new engine loaded from that same database had `reloaded_ban=false`. The expected persistence assertion failed. This fault injection demonstrates lost revocation, not corruption of a committed payment.

**A10-02 · P3 · Automatic cartel detection on an objective-state merge is unproved.** Production code receives/validates `ShardEquivocation` proofs, but the searched production tree contains no constructor for those original-vote proofs; the automatic two-attestation construction is in the simulation resolver. Sync intentionally transfers objective locks without historical signature bundles. Therefore a merge containing conflicting state does not itself prove all cartel members signed twice. Receiving one externally supplied genuine proof works; automatic extraction from two separately observed original approvals needs dedicated production evidence. This is a detection/integration gap, not permission to ban honest losing-branch signers or add historical receipt archives.

The prompt's unconditional takeover-immunity claims do not hold. Fourteen colluders can sign both conflicting digests: an executed shared-protocol verifier probe accepted both 14-signature proofs, as cryptographic verification must. Owner signatures still prevent inventing another holder's authorization, but cannot prevent an owner and captured quorum cooperating on two authorized conflicting spends. The usual safety argument assumes a bounded adversary and one justified committee. Two 14-of-20 sets overlap in at least eight identities; only demonstrated double-signers can be sanctioned. Seven withheld votes stop FINAL. Another gateway cannot change that shard or substitute ranks 21–40. Later class-first/min-hash convergence does not undo delivered goods. No proof shows identity/ticket loss always exceeds the attacker's profit.

Under a fixed, unground, uniformly sampled eligible population, `P(X>=14) = sum[C(K,j) C(N-K,20-j)] / C(N,20)`. Exact Python integer arithmetic gave, for N=1000, probabilities 9.82228e-11 (K=100), 1.36687e-6 (K=200), and 2.25628e-4 (K=300) for a specified shard. At K=300 the expected number across 65,536 shards is about 14.79; expectation needs no shard-independence assumption. These are conditional model calculations, not measured attack costs. Targeted ticket grinding, biased admission and different local rosters invalidate the uniform-selection premise; 24h ticket maturation delays use but does not prove capture impossible.

## Integrated fix plan

1. Add a durable evidence-plus-ban operation with bounded admission and acknowledgment off the runtime thread. Preserve immediate RAM rejection, but retain/retry failed durable sanctions or replay strictly verified stored evidence before restart admission. Never report durable success merely because queueing failed; retain bounded backpressure and fail closed.
2. Preserve the real-QUIC worker-failure regression; add queue-full, restart, evidence replay, corrupted evidence and reopened database cases. Verify ticket exclusion and WoT edge removal after recovery as well as immediate local rejection.
3. When two genuine incompatible original approvals are actually available, create bounded full-key evidence and submit it through the existing fraud-proof stream. Test acquisition, exact network/slot/purpose checks and multi-hop forwarding; ordinary live-state revisions must not count as equivocation. Do not invent proof from hashes or add lock gossip.
4. Keep the conditional takeover/censorship model explicit in client/operator documentation and tests. Do not implement suspicion-based bans, financial deposits or automatic committee expansion/reshuffling. Re-run the standard and adversarial wire suites before closing either finding.
